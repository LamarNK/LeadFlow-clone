# Пропущенные входящие: история и уведомления

## Пользовательское поведение

- В меню CRM и внизу колокольчика есть ссылка «Пропущенные звонки».
- История `/Crm/MissedCalls` показывает входящие со статусами `missed`, `rejected`, `failed`. Исходящие, принятые и неподтверждённые (`unknown`) не включаются.
- Доступны период (по умолчанию последние 7 календарных дней), фильтр результата, пагинация по 30 записей и фильтр ответственного для существующих старших ролей.
- Клик по уведомлению открывает доступную карточку кандидата. Без доступной карточки открывается конкретный звонок через `callId`, независимо от давности звонка. Авторизация и офисные ограничения при этом не обходятся.
- Номер, время, результат, линия и ответственный доступны в истории. Кнопка перезвона использует существующую телефонию, а не новый механизм набора.
- Прочтение уведомления не удаляет звонок. История не является очередью задач «ещё не перезвонили»: последующий исходящий тоже не скрывает прошлый входящий.

## Источник данных и права

Источник — сохранённые `CrmCalls`, не ограниченная лента уведомлений и не наличие записи разговора. Для известных карточек используется текущий ответственный, для неизвестного номера — привязанный к вызову менеджер линии. Без обоих ответственных вызов виден только существующим старшим ролям в рамках их офисного доступа.

Новые права, роли и расширения доступа не добавляются. Привязка линии не даёт менеджеру доступа к неназначенной карточке. Карточки, перенесённые в другой офис, не раскрываются через строку старого офиса.

## Надёжность уведомлений

Новые уведомления о пропущенном имеют `Id`, равный `CrmCalls.Id`. Повторная доставка не создаёт второй такой же alert. Событие с уточнением `unknown → missed` создаёт уведомление; `missed → answered` исключает его из выдачи и непрочитанного счётчика. Поздний непринятый/неизвестный результат не понижает уже подтверждённый `answered`.

Если неизвестный номер позже сопоставлен с карточкой существующим механизмом reconciliation, ссылка в уведомлении обновляется только при совпадении ответственного карточки с получателем.

`BUSY` не доказывает, что менеджер вручную отклонил вызов, поэтому интерфейс пишет «Отклонён / занято». Правила `DIALSTATUS` сверены с [официальной документацией Asterisk Dial](https://docs.asterisk.org/Certified-Asterisk_22.8_Documentation/API_Documentation/Dialplan_Applications/Dial/).

## Границы решения и выпуск

- Требуется обновление API и Web. Миграций БД и изменений dialplan нет.
- Существующая история сохранённых звонков сразу доступна; массовая генерация старых уведомлений не выполняется.
- Старые уведомления с произвольными ID сохраняются. Их нельзя надёжно сопоставить с исправленным вызовом без отдельной миграции данных, поэтому сопоставление по догадке не делается.
- Вызов, не дошедший до Asterisk или не переданный в CRM, нельзя восстановить из отсутствующего события. Также нельзя достоверно разделить разные телефонные плечи, если провайдер прислал их с разными несвязанными ID.
- Проверки: тесты webhook/статусов, уведомлений, офисных прав, дат и запросов InMemory/SQLite; локальный браузер на синтетических звонках — переход в карточку, fallback без карточки, счётчик прочтения и фильтрация. Реальные звонки и production-проверки не проводились.
