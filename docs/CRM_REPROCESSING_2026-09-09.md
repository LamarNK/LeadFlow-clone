# Повторная обработка НДЗ

## Согласованный объём

Серверный read-only срез: 1 135 карточек, **сейчас** закрытых по НДЗ с 07.09 по
09.09.2026 включительно (UTC+5). Офисы: 1 — 304, 2 — 90, 3 — 217, 4 — 268,
6 — 256. Тестовый офис исключён. Это срез, а не зафиксированный список: до
включения правила пользователь может открыть карточку или поменять причину.

Офис назначения: `def514aa-43c5-4bf8-a9e3-c751372b2133`, «Повторная обработка».
На последней проверке IsEnabled=true, **CrmEnabled=false**. Ничего на сервере
этой разработкой не менялось. Само обновление бинарников правило не включает.

## Правило

- Фоновая обработка по умолчанию каждые 10 секунд, не более 25 карточек за цикл.
- Только перечисленные исходные офисы, текущий IsClosed=true, причина НДЗ,
  ClosedAtUtc не раньше явно заданной даты. Пустая дата запрещена.
- Офис назначения исключён всегда, даже если он оказался в списке исходных.
- Включение с границей 07.09 одновременно постепенно обработает согласованный
  остаток и будет подхватывать все последующие закрытия. Старые закрытия до
  07.09 не затрагиваются. Если старая карточка будет вновь закрыта по НДЗ после
  границы, это уже новое подходящее закрытие.
- Другие причины, открытые карточки, карточки без даты закрытия не переносятся.
- Перед запуском принимающий офис должен быть включён, принимать CRM и иметь
  этап с точным именем «Лид». При ошибке карточки остаются закрытыми в исходном
  офисе; цикл повторяется, причина пишется в лог API.

Переносится **та же карточка**, без копирования и изменения ResponseId/PersonId.
Запись Closed остаётся с исходным актором и офисом. Добавляются ReprocessingSent,
Reopened и ReprocessingReceived. Для старой истории без OfficeId сохраняется
использовавшийся до переноса fallback и выставляется ContextInferred=true.
Сохраняются поступление в CRM и первичное назначение: повторная обработка не
становится новым рекламным лидом. LastContactAtUtc не подменяется автопереносом.

В назначении: сначала снимается прежний ответственный, затем используется обычная
дневная очередь нового офиса. Нет подходящих менеджеров на смене/идёт сбор смены —
карточка остаётся в очереди «Лид» нового офиса. Старые открытые задачи отменяются
(не удаляются), их уведомления погашаются, запланированные сообщения отменяются.
Заметки, файлы, завершённые задачи, звонки и прежние номера не удаляются.

Перенос и история сохраняются одной транзакцией. PostgreSQL использует advisory
lock на цикл между репликами и FOR UPDATE SKIP LOCKED на карточки. После блокировки
условия перепроверяются. Повторный запуск не переносит уже переданные карточки.
OfficeId/IsClosed защищены EF concurrency tokens: устаревшее действие менеджера
после переноса получает 409 с просьбой обновить страницу. SQL-изменений схемы
для этих двух concurrency tokens нет.

## Телефоны

При совпадении кандидата по существующим правилам новый входящий номер добавляется
в CandidatePhoneHistory и CandidateContactPhones, привязанные к PersonId, независимо
от текущего офиса CRM. Контакты получают кнопку «Позвонить». Старые контакты и
выбранный основной номер в списке контактов сохраняются. Обновление того же
исходного отклика, как и раньше, обновляет его PhoneRaw/PhoneNormalized.

PhoneChanged у кандидата, уже имеющего CRM-карточку, больше не порождает вторую
CRM-карточку при автоматической доставке. Исходный отклик и метрика изменения
номера сохраняются, CRM получает дополнение контактов. Новый номер появляется
после обновления карточки; уведомление об изменении отправляется её текущему офису.

Правила идентификации не ослаблялись: полное ФИО — поиск по откликам за 6 месяцев;
неполное имя — дополнительные совпадения возраста/города и окно ±7 дней по отклику.
Произвольно однофамильцев или отклики, которые эти правила не сопоставили, правило
повторной обработки не объединяет. Уведомления менеджеру «пришёл новый номер»
отдельной новой подсистемой не добавлялись.

## Активация после выкладки и проверки

1. Снять резервную копию БД штатным способом и повторить read-only подсчёт по датам.
2. В обычном администрировании включить CRM у указанного офиса и проверить «Лид»,
   список менеджеров и их смены. Не изменять API/Bitrix-офис исходных откликов.
3. К **существующему** набору compose-файлов добавить `docker-compose.reprocessing.yml`.
   Не запускать этот override как самостоятельный стек.
4. Значения переменных для согласованного режима (никаких секретов здесь нет):

```dotenv
CRM_REPROCESSING_ENABLED=true
CRM_REPROCESSING_OFFICE_ID=def514aa-43c5-4bf8-a9e3-c751372b2133
CRM_REPROCESSING_CLOSED_FROM_UTC=2026-09-07T00:00:00+05:00
CRM_REPROCESSING_BATCH_SIZE=25
CRM_REPROCESSING_INTERVAL_SECONDS=10
```

Включение — операция с данными, не просто preview. Пересоздание только API с
обновлённым окружением кратковременно влияет на запросы CRM; согласовать окно.
Не перезапускать PostgreSQL, Asterisk и остальные сервисы ради этого правила.
Для режима только будущих закрытий вместо 07.09 задаётся точный момент включения.
Для остановки новых переносов установить Enabled=false и применить окружение API.
Это не откатывает уже перенесённые карточки; автоматического обратного переноса нет.

После активации: проверить пачки в логах, несколько карточек в новом офисе,
сохранение Closed в истории старого офиса, очередь/назначение, новый номер у тестового
кандидата и отсутствие повторного переноса при закрытии внутри нового офиса.
Отбор без верхней даты намеренный: правило должно продолжать работать после 09.09.

## Проверки разработки

InMemory и SQLite: граница 07.09 00:00 UTC+5, предыдущий момент, старые/новые дни,
исключённые офисы, переоткрытые/другая причина/нет даты, неготовый офис, ограничение
пачки, перезапуск, закрытие внутри назначения, конкурирующее редактирование,
сохранение исходного менеджера в аналитике, новые номера после реального переноса,
повторная доставка номера. Отдельно — регрессия CRM, аналитики и сопоставления.

Итоговый прогон: **236 пройдено, 0 ошибок**, включая назначение по смене нового
офиса и откат карточки, истории, задач и контактов при ошибке сохранения.
Release-сборки API и Web успешно завершались. В браузере проверен вывод старого
и нового синтетических номеров с отдельными кнопками «Позвонить»; реальных звонков
не совершали. Визуальная проверка использовала новый Web и прежний локальный
демо-API, а перенос и поступление нового отклика проверены сервисными тестами.

При повторном прогоне на C: закончилось место, из-за чего возникли ошибки
создания файлов и сборки. Удалены только созданные этой задачей временные
Release-сборки (около 88 МБ), после чего итоговый прогон прошёл полностью.
Временный Web на 5283 остановлен; основной демо-стенд 5280/5281 не останавливался.

Настоящий PostgreSQL в этой локальной среде пока не проверен: Docker Desktop engine
недоступен. До включения в прод требуется проверка этого пути на тестовом PostgreSQL.
