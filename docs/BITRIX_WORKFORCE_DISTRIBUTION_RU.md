# Распределение сделок Bitrix24 по рабочей смене

Модуль переносит известное поведение внешнего проекта `Andrey2` в `Orbita.Api` и не добавляет отдельный сервис или новый стек. Реализация использует ASP.NET Core, EF Core и PostgreSQL из существующего решения LeadFlow.

## Что реализовано

События `ONCRMDEALADD` и `ONCRMDEALUPDATE` поступают в публичный endpoint Orbita, проверяются по `application_token`, домену портала и при наличии по `member_id`, после чего попадают в устойчивую очередь PostgreSQL. Дополнительная сверка `crm.deal.list` раз в минуту восстанавливает события, которые исходящий webhook не доставил.

| Сценарий | Source | Target | Время |
| --- | --- | --- | --- |
| Новая сделка | `NEW` | `NEW` | сразу |
| НДЗ | `UC_FU2T4L` | `UC_FU2T4L` | 08:00–11:00 МСК |
| НДЗ 2 | `UC_ENSD7E` | `UC_FU2T4L` | 08:00–11:00 МСК |
| НДЗ с подменным | `UC_6OQRTF` | `UC_6OQRTF` | 08:00–11:00 МСК |
| НДЗ с подменным 2 | `UC_WT8KQY` | `UC_6OQRTF` | 08:00–11:00 МСК |

Все ID задаются в панели отдельно для каждого портала и не зашиты в обработчик.

Менеджерами считаются только активные пользователи Bitrix24 со статусом рабочего дня `OPENED` или `PAUSED`. Выбор выполняется по кругу. При отсутствии доступных менеджеров задание остаётся в очереди.

Для утренних сценариев поддержан резерв позднего выхода: первый менеджер получает настраиваемую долю очереди, остаток ждёт второго менеджера не более заданного времени и не позже конца утреннего окна.

Дополнительно модуль:

- переносит вторичную стадию НДЗ в основную;
- меняет ответственного сделки и при включённой опции связанных контактов;
- заполняет пустые поля «Возраст», «Вакансия/Профессия» и «Город» из комментария Авито;
- не меняет ответственного у вручную созданной менеджером сделки `NEW`, если отсутствует маркер LeadFlow;
- защищён от повторных webhook-событий, повторов REST-записи и параллельной обработки одной сделки.

## Режимы

- `disabled` — очередь не обрабатывается;
- `shadow` — решения рассчитываются и попадают в журнал, Bitrix24 не изменяется;
- `writer` — разрешены изменения сделок и контактов.

Первый переход в `writer` разрешён только из сохранённой конфигурации `shadow` без изменения менеджеров, стадий и остальных правил. При замене входящего REST-вебхука модуль автоматически переходит в `disabled`, отменяет очередь старого портала и сбрасывает состояние round-robin.

## Что требуется в Bitrix24

1. Входящий REST-вебхук с правами:
   - CRM;
   - пользователи;
   - учёт рабочего времени.
2. Исходящий webhook на события:
   - `ONCRMDEALADD`;
   - `ONCRMDEALUPDATE`.
3. `application_token` исходящего webhook.
4. Подтверждённые:
   - ID воронки;
   - ID стадий;
   - Bitrix ID менеджеров;
   - коды пользовательских полей сделки.

Коды полей «Идемпотентность», «Возраст», «Вакансия/Профессия» и «Город»
задаются отдельно для каждого экземпляра Bitrix в админской панели. Пустой код
отключает заполнение соответствующего поля для этого портала. Перед первым
включением `writer` модуль через REST проверяет доступность воронки, всех
включённых стадий, всех непустых кодов полей и каждого настроенного менеджера.
Статус рабочего дня `CLOSED` не мешает сохранить `writer`, но такой менеджер не
получает сделки до перехода в `OPENED` или `PAUSED`.

Секрет REST-вебхука хранится зашифрованным через Data Protection. `application_token` исходящего webhook хранится только как SHA-256-хеш и после сохранения не возвращается в UI.

## Настройка

1. Развернуть Orbita с PostgreSQL и указать публичный HTTPS-адрес API:

   ```env
   BITRIX_WORKFORCE_PUBLIC_BASE_URL=https://api.example.ru
   ```

2. В панели открыть «Настройки → Интеграции», выбрать нужный портал Bitrix24.
3. Сохранить менеджеров, воронку, стадии и параметры в режиме `shadow`.
4. Настроить receiver и скопировать показанный endpoint в исходящий webhook Bitrix24.
5. Проверить журнал решений минимум на одной тестовой сделке и двух тестовых менеджерах.
6. Отключить старый обработчик `Andrey2`.
7. Не меняя параметры, выбрать `writer`, подтвердить проверку правил и сохранить.

Нельзя одновременно держать `Andrey2` и LeadFlow в режиме записи: оба обработчика могут назначить разных ответственных.

## Обязательная проверка перед production

Проверка выполняется на реальном PostgreSQL 16:

1. Отправить два параллельных события одной тестовой сделки.
2. Убедиться, что выполнена одна REST-запись и курсор round-robin сдвинулся один раз.
3. Проверить очередь более чем из 50 сделок, включая переход на следующую страницу `crm.deal.list`.
4. Проверить утро с одним менеджером, затем выход второго менеджера.
5. Проверить отключение `writer` во время обработки: новые изменения контактов выполняться не должны.
6. После успешной проверки оставить `shadow` минимум на одно полное утреннее окно, затем включить `writer`.

PostgreSQL-проверка конкурентной обработки включена в `Orbita.Tests` и запускается
только при наличии отдельной тестовой базы:

```powershell
$env:ORBITA_TEST_POSTGRES_CONNECTION_STRING='Host=localhost;Database=orbita_test;Username=orbita_test;Password=change-me'
dotnet test Orbita.Tests\Orbita.Tests.csproj --filter "FullyQualifiedName~BitrixWorkforcePostgreSqlTests"
```

Пользователь тестовой базы должен иметь право создавать и удалять схемы. Тест
создаёт уникальную временную схему, применяет в ней миграции, параллельно
обрабатывает два события одной сделки и затем удаляет схему.

## Матрица перехода по офисам

Перед отключением любого варианта `Andrey`, `Andrey2` или `Andrey3` для каждого
портала отдельно заполните и согласуйте:

| Параметр | Что зафиксировать |
| --- | --- |
| Офис и портал | Название офиса и домен Bitrix24 |
| Старый обработчик | Точный URL/вариант и ответственный за его отключение |
| Воронка | `CATEGORY_ID` |
| Правила стадий | Сценарий, source, target и утреннее окно |
| Менеджеры | Bitrix ID в фактическом порядке round-robin |
| Время | IANA timezone, начало/конец окна и резерв позднего выхода |
| Поля | UF-коды идемпотентности, возраста, профессии и города |
| Дополнительное поведение | Синхронизация контакта, сохранение ручного владельца, проверка дублей |
| Приём событий | Новый входящий REST-вебхук, исходящий webhook и `member_id` |
| Приёмка | Полное окно `shadow`, сверка решений и согласовавший сотрудник |

Переключение выполняется портал за порталом. Сначала старый обработчик перестаёт
писать в Bitrix24, затем без изменения проверенных правил включается `writer`.
Для отката новый модуль переводится в `disabled` до повторного включения старого
обработчика.

Точная доля утренней выдачи из старого `Andrey2` неизвестна, поэтому она оставлена явной настройкой. До подтверждения владельцем процесса рекомендуется начинать с 50%.
